Executive Summary

The Em-Cubed codebase shows clear signs of rapid feature accretion without proportional structural refactoring. The most acute friction points are: a God-class base that imports 12+ subsystems, a 400-line MCP dispatcher that instantiates every subsystem inline, two competing checkpoint systems, and a surface layer that has grown to 16 implementations without a consistent internal contract.

1. Extract Ontology Dependencies from BaseLoopySkill

src/em_cubed/loopy/base.py — Lines 43-339

Strong

Problem

BaseLoopySkill is the single worst locality offender. A developer must read 12+ unrelated ontology modules to understand what it means to be a loopy skill. The constructor directly instantiates OntologyLedgerValidator() and 12 methods are hardcoded to call specific ontology classes. There is no interface, no protocol, no dependency injection.

Solution

Introduce a SurfaceExecutionContext protocol that provides verify(), induce_concept(), compute_derived_property(), etc. The base class becomes a loop engine that calls context.verify(state) instead of self.verify_topos(state).

2. Decompose MCP call_tool() into a Tool Registry

src/em_cubed/gateway/mcp_server.py — Lines 214-418

Strong

Problem

The call_tool() method is a 200-line if/elif chain. Each branch imports and instantiates a different subsystem inline. To understand what the MCP server does, you must read 8+ unrelated modules. There is no delegation, no routing table, no plugin architecture for tools.

Solution

Introduce a ToolRegistry with register(name, handler) and dispatch(name, args). Each subsystem registers its own tools. The MCP server becomes a thin transport layer.

3. Unify Competing Checkpoint Systems

workflow/durable_execution.py vs workflow/checkpoint.py

Strong

Problem

Two separate checkpoint implementations serve the same purpose but have different schemas and APIs. durable_execution.py (97 lines) uses a simple SQLite table. checkpoint.py (417 lines) is a complex system with Checkpoint dataclass, CheckpointStorage ABC, FileCheckpointStorage, CheckpointManager, plus integration with CausalDAG, HypergraphStore, and CompactionPipeline.

Solution

Make CheckpointManager the single checkpoint API. Have durable_execution.py delegate to CheckpointManager instead of implementing its own SQLite schema. Extract a CheckpointStorage interface and have both use it.

4. Create SurfaceFactory to Eliminate Sandbox Duplication

src/em_cubed/surfaces/ — All 16 surface implementations

Strong

Problem

16 surface files, each reinventing the same restricted interpreter setup. python_surface.py and z3_surface.py both create asteval.Interpreter with different sandboxing strategies. Each duplicates _BLOCKED_SYMBOLS, extract_tags(), and _execute_impl() patterns. No shared abstraction.

Solution

Introduce a SurfaceFactory or RestrictedExecutionContext that handles common asteval/sandbox setup, timeout management, and concurrency limiting. Each surface only provides _execute_impl() and extract_tags().

6. Isolate _execute_distributed_task from Plugin Stack

src/em_cubed/workflow/distributed.py — Lines 238-281

Worth Exploring

Problem

_execute_distributed_task is a module-level function that imports PluginManager, SkillRegistry, SkillExecutor, and SkillExecutionRequest inside its body. This function runs in a separate process via ProcessPoolExecutor, yet it re-implements the entire plugin loading and skill resolution stack inline.

Solution

Pass a serialized skill specification to the worker process instead of re-resolving it from the registry. The worker should receive (skill_id, code_blocks, surface_name, input_data) and execute them without touching PluginManager or SkillRegistry.

Before (Coupled)

After (Isolated)

graph TD PE["ProcessPoolExecutor"] -->|spawns| PDT["_execute_distributed_task()"] PDT -->|"receives serialized spec"| SPEC["(skill_id, code_blocks,
surface_name, input_data)"] SPEC -->|"no registry needed"| EXEC["Execute directly"] style PE fill:#10b981,stroke:#059669,color:#fff style SPEC fill:#3b82f6,stroke:#2563eb,color:#fff

Benefits

  • Locality: Worker logic is self-contained; no need to understand the plugin stack to test it.
  • Leverage: The worker becomes a pure function of its inputs; easier to reason about and debug.
  • Testability: Unit tests can call the worker directly with a fake spec, no ProcessPoolExecutor needed.

Top Recommendation

Start with Candidate 1: Extract Ontology Dependencies from BaseLoopySkill. It has the highest impact because BaseLoopySkill is the single largest locality/coupling problem in the codebase. Deepening this module immediately improves testability for all loopy skills and establishes a context-protocol pattern that can be reused elsewhere. It also reduces the cognitive load for anyone working on the ontology subsystem, since the base class will no longer be a forced dependency.
